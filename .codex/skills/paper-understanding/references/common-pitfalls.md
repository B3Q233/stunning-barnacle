# 常见的论文理解错误案例

填写理解文档前快速过一遍，避免重复踩坑。

## 1. 损失函数遗漏权重系数/辅助项

**典型错误**：只把主损失公式抄下来，漏掉论文里用小字或附录提到的权重系数 λ，或者漏掉辅助损失（如对比学习中的正则项、多任务学习中的辅助任务损失）。

**对策**：写损失函数部分时，专门搜索全文中所有带 λ、α、β 等希腊字母系数的公式，逐一核对是否都已记录。附录和"实验设置"章节是高发区。

## 2. 预处理步骤"想当然"

**典型错误**：论文只说"我们对数据进行了标准化处理"，AI 直接假设是 Z-score 标准化并据此写代码，但实际官方代码用的是 Min-Max 归一化。

**对策**：遇到模糊的预处理描述，必须标【AI推断补全】，并在交付时在"关键缺口"列表里特别提示用户——这类细节往往直接影响复现指标，是最值得人工核实的地方。

## 3. 模型结构层级拆分与架构图不一致

**典型错误**：论文架构图里有一个跳跃连接（skip connection）或某层的输出被复用到后面多个模块，但文字描述时容易把这种"非线性"的数据流简化成线性的层级列表。

**对策**：写模型结构部分时，逐层对照架构图，特别注意箭头的分支和汇合点，不要只读正文文字描述。

## 4. 评估协议细节被忽略

**典型错误**：只记录了用什么指标（如 Recall@K），但漏掉了评估时的负采样策略、是否过滤了训练集中出现过的样本等协议细节——这些细节对最终指标数值影响很大，常是"复现指标对不上"的根源。

**对策**：评估方式部分要专门检查论文的"实验设置"章节是否提到采样策略、过滤规则等，这部分常被一带而过，容易漏看。

## 5. 超参数表格散落在多处

**典型错误**：正文提到一部分超参数，附录的表格里又补充了另一部分，甚至两处数值有细微差异（比如不同数据集用不同的学习率），只记录了正文里看到的那一份。

**对策**：填写超参数表格前，专门检索全文是否有附录表格，且要注意论文常对不同数据集/不同实验设置给出不同的超参数值，不要把所有情况混为一谈。

## 6. 把"官方代码默认值"当成"论文报告值"

**典型错误**：在做交叉验证时，如果某个超参数论文未提及，但官方代码仓库的 README 或脚本里有一个默认值，容易直接把这个默认值标注为【论文明确写出】。

**对策**：来自代码的信息应标注来源为"官方代码"，与"论文明确写出"严格区分，即使两者最终数值一致，来源标注也不能混淆——这是为了让后续如果论文和代码出现矛盾时，使用者能清楚地知道这条信息的可信度层级。

## 7. 正则化项的 PyTorch API 用错，强度差一个数量级

**典型错误**：论文公式里的正则化项写的是 $\|W\|^2$（权重的平方和），写代码时直接用 `W.norm(p=2)` 实现——但 `.norm(p=2)` 算出来的是 L2 范数（即开根号后的结果），并不是平方和，少了一步平方，导致实际的正则化强度比论文小了一个数量级，且这个错误不会报错，只会让模型表现"差一点但说不清哪里差"。

**对策**：理解文档里凡是出现正则化项，必须明确写出公式对应的 PyTorch 实现方式（如 `(W**2).sum()` 或 `W.norm(p=2).pow(2)`），不要只记录公式本身、把实现细节留给写代码的环节再决定——这类陷阱在理解阶段就要预先标注出来，提醒后续实现时注意。同样要注意不同优化器自带的 `weight_decay` 参数实现方式不同（Adam 和 AdamW 对 weight decay 的处理不等价），如果论文用的是某个特定优化器的 weight decay，要确认 PyTorch 对应优化器是否是同一种实现。

## 8. 初始化方式被忽略，当成"无所谓的细节"

**典型错误**：论文里某一句话提到"权重使用 Xavier 初始化，Embedding 使用标准差 0.01 的正态分布初始化"，这种细节容易被当作无关紧要的实现细节直接跳过，理解文档里完全没有记录初始化方式这一项。

**对策**：初始化方式的偏差不会让代码报错，只会让训练轨迹和最终收敛点产生偏差，且很难定位——因为这类问题表现为"训练能跑、loss 下降趋势正常，但最终指标就是比论文差一点"，排查时容易被误判为别的原因（数据问题、超参问题）。理解文档必须专门列出权重/偏置/Embedding 各自的初始化方式，哪怕论文只是一句话带过也要记录，并标注来源段落。

## 9. 正则化手段分散在全文各处，只记录了损失函数公式里写出的那一项

**典型错误**：论文损失函数公式里只写了主损失 + 一个 L2 正则项，理解文档照着公式抄了下来就认为正则化部分已经完整，但实际上论文的"训练细节"或"实验设置"章节里还提到了 dropout、early stopping、label smoothing 等其他正则化手段，这些不会出现在损失函数公式里，只会用文字描述。

**对策**：填写正则化清单时不能只看损失函数公式，必须专门通读全文搜索 dropout/early stopping/label smoothing/gradient clipping/noise injection 等关键词，逐一确认是否被论文使用，哪怕某一项确认"论文未提及"也要明确记录排查过，而不是因为没去找就漏掉。

## 10. 数据文件格式被假设，未经实际核对

**典型错误**：论文给出了数据集名称（如 Gowalla），但原始数据文件（train.txt / test.txt）的实际格式有多种可能：NGCF 格式是每行 `user_id item1 item2 item3 ...`（一用户多物品），而其他来源可能是 `user_id item_id` 成对格式（每行一个交互对）。理解文档只记录了"数据从哪里下载"，没有确认**文件的真实格式**，导致预处理代码按错误的格式解析——如果多物品格式被当成成对格式读取，每行只取第一个物品，会丢失 97% 的交互数据。这个错误不会报错，数据量看起来也"正常"（29K 用户能正确识别），模型也能跑，但图上几乎没有边可以传播信息，训练结果必然失败。

**对策**：
1. 理解文档的「1.3 数据结构」中**必须**逐文件描述真实格式（每行几列？每列含义？分隔符？编码？），不能只写"user_id 和 item_id 的交互对"这种泛泛描述
2. 建议直接 `head -3 train.txt` 粘贴前三行原文到理解文档中
3. 预处理脚本运行后，**必须**打印实际读取的交互总数，并与论文 Table 2 中报告的数据集规模对比（如 Gowalla 应为 1,027,370 条），如果不一致立即报警

## 11. 把第三方参考实现当成论文 ground truth

**典型错误**：论文有官方代码（作者本人发布在 GitHub），但在复现时找了另一个"看起来差不多"的第三方实现作为参考对照。第三方实现可能出于各种原因（适配不同数据集、作者自己的 tuning、理解偏差）偏离了论文的原始设定——例如本次的第三方参考代码（lightGCN-MY）在初始化方式（Normal vs 论文的 Xavier）、dropout 策略（加了 graph dropout vs 论文说不需要）、embedding 架构（分离式 vs 论文的合并式）三处与论文不一致。如果把第三方代码的行为当成"论文应该怎么做"，就会在错误的基准上进行修复。

**对策**：
1. 理解文档必须区分三个信息源层级：
   - **A 级**：论文原文（最高权威）
   - **B 级**：论文作者发布的官方代码（若论文和代码有矛盾，以论文为准但标注差异）
   - **C 级**：第三方实现（仅作参考，任何与论文不一致的地方默认认为论文是对的）
2. 在模板的「与官方代码的交叉验证」部分，必须明确代码来源的层级
3. 做任何"根据参考代码修复"的操作前，先回论文原文逐句核实——如果参考代码和论文冲突，优先跟论文

## 12. 攻击/投毒/对抗类论文的"动态数据注入"模式被忽略

**典型错误**：论文方法包含"向训练数据注入假用户/假样本"的步骤（投毒攻击、对抗训练、数据增强等常见）。理解文档只记录了"正常训练用的静态数据集"，没有标注**哪些数据结构在攻击/注入过程中需要动态扩展**。例如本次论文（NDSS 2021 投毒攻击）的 Algorithm 1 每轮注入一个新假用户到训练集，这意味着用户数、训练矩阵尺寸、Embedding 表大小都在逐轮变化。理解文档如果只记录了初始的静态规模（943 users），下游实现就会写出 size=943 的固定矩阵，假用户 ID=943 直接越界。

**对策**：
1. 理解文档「模块二」中必须单独一节（建议加在 2.3 模型结构之后，如 2.3.3「数据流与生命周期」），标注：
   - 哪些数据结构是**静态的**（预处理后不再变化）——如物品总数 N
   - 哪些数据结构是**动态的**（攻击/训练过程中会扩展）——如用户数 M、训练交互矩阵
   - 动态扩展的触发时机和扩展量——如"每生成 1 个假用户，M 增加 1"
2. 在自查清单中增加一项：对于包含数据注入/投毒/对抗训练的论文，是否已识别并标注了动态数据结构？
3. 理解文档的"关键缺口"汇总中，必须提醒下游实现者"训练循环中用户/物品数会动态变化，不要用固定尺寸的容器"
