# 论文理解 Skill

将一篇论文转化为结构化理解文档，作为论文复现工作流的"地基"。这份文档之后会被人工审核（检查点①），审核通过后将作为后续所有代码编写 skill 的**唯一事实来源（single source of truth）**，因此准确性和诚实标注比覆盖面更重要。

## 核心原则：诚实标注，不要填坑

写这份文档时最容易犯的错误是：论文没写清楚的细节，凭"行业常见做法"或"看起来合理"的方式直接编一个答案填进去，且不说明这是推断。**这是绝对禁止的。**

每一条具体信息（尤其是数值型超参数、预处理步骤、训练设置）必须标注来源等级：

- **【论文明确写出】**：原文有直接陈述、公式、表格或图示支持，可以引用原文段落或图表编号
- **【AI推断补全】**：原文没有直接给出，是根据上下文/惯例/同领域常见做法推断的。必须说明推断依据，且依据要合理（如"参考该数据集在其他论文中的常见设置"），不能凭空捏造
- **【论文未提及】**：原文完全没有相关信息，且也无法合理推断。直接留空标注，不要硬填
- 【**论文不明确**】：原文中提供方法模糊，就提供多种备选的方法（例如：初始化方法）

如果一个字段你不确定该归入哪一类，宁可标注为"论文未提及"并提示用户去看官方代码或联系作者，也不要冒险归入"论文明确写出"。

## 工作流程

### 第一步：定位输入材料

- 如果用户提供了论文 PDF，使用 PDF 阅读相关工具（参考 pdf-reading skill）读取全文，包括正文、图表、公式、附录——**附录里常藏着关键的超参数表，不要漏看**

**硬性规则：文字提取看不到图表，遇到架构图/公式/表格必须光栅化对应页面用视觉确认，不能只依赖文字提取。**

文字提取（`pdftotext`/`pdfplumber`）对叙述性文字是够用的，但对以下三类内容是"瞎的"，必须把对应页面渲染成图片后用视觉阅读：

- **模型架构图**：文字提取完全看不到箭头走向、分支、跳跃连接，只读文字描述极易把非线性的数据流简化成错误的线性结构（这正是模块二·2.3 模型结构最容易出错的来源）
- **公式**：复杂公式（多层上下标、求和符号、矩阵运算）文字提取常常乱码或丢失结构，必须视觉确认公式的真实样子，再手动还原成 LaTeX
- **表格**：先用 `pdfplumber` 的 `extract_tables()` 尝试，如果提取结果错位、列对不齐（论文表格常见，尤其是多行表头或合并单元格），改用光栅化页面直接视觉读取，不要将提取错位的表格内容直接当真填进理解文档

具体操作：

```bash
# 先做内容盘点，判断是否有文字层
pdfinfo paper.pdf
pdffonts paper.pdf
pdfimages -list paper.pdf

# 定位到包含架构图/公式/表格的具体页码后，光栅化该页
pdftoppm -jpeg -r 150 -f <页码> -l <页码> paper.pdf /tmp/page
```

然后直接 view 渲染出的图片，把视觉读到的内容（架构图的真实数据流、公式的真实形式、表格的真实对齐）作为理解文档的依据。**矢量图陷阱**：如果论文图表是 matplotlib/Excel 类工具生成的矢量图（很常见），`pdfimages` 提取不到（只抓嵌入的位图），这种情况必须用 `pdftoppm` 整页光栅化才能看到，不要因为 `pdfimages -list` 没列出图片就误以为该页没有图表。

- 主动询问用户是否有官方代码链接（GitHub 等）。如果有，先不要直接看代码细节，而是先完成基于论文本身的理解文档，再用官方代码做交叉验证补充——这样能保留"论文实际写了什么"和"代码里实际怎么做"两条独立信息，便于后续发现两者不一致的地方（这本身就是有价值的发现，要在文档里标注出来）
- **区分信息源层级**：论文复现时可能接触多种代码，但可信度不同：
  - **A 级**（最高）：论文作者发布的官方代码
  - **B 级**（最高）：论文原文明确写出的内容（公式、表格、数值）
  - **C 级**（仅参考）：第三方实现、社区复现
  - A 级和 B 级冲突时以 B 级为准。**严禁**基于 C 级代码的"好结果"反推论文应该怎么做
- 如果论文中提到的细节在正文和附录中有冲突，两者都要记录，并标注冲突

### 第二步：填充四模块字段模板

按照下方的 `references/template.md` 填写文档。四大模块、固定字段，不要自创字段结构（一致的格式是为了让多篇论文的理解文档可以互相对比、可以被下游 skill 稳定解析）：

**模块一：数据集**
- 数据组成（训练/验证/测试划分、规模、是否有辅助数据）
- 获取方式（数据集名称、版本、官方下载渠道——只记录来源，不要自动下载，提醒用户手动下载并核对版本）
- 数据结构（字段含义、**真实文件格式**——粘贴 `head -3` 原文到文档中、维度）
- 预处理方式（具体步骤，若论文描述模糊则标【AI推断补全】并说明依据）

**模块二：模型**
- 输入（张量形状、特征类型）
- 输出（预测目标形式）
- 模型结构（分层级描述每个模块作用，越具体越好，必要时用文字描述结构图）
- 损失函数（公式用 LaTeX 还原，注明所有权重系数/正则项，不要漏掉论文里提到但容易被忽略的辅助损失项）
- 评估方式（具体指标、评估协议如负采样策略、在哪个数据子集上评估）
- 正则化技术清单（逐项列出 λ/weight decay/dropout/early stopping 等手段，标注每项的 PyTorch 实现注意事项）
- 初始化方式（权重/偏置/Embedding 各自的初始化分布和参数，逐项标注论文出处段落）

**模型结构必须图文结合还原，不能只读正文文字。** 很多论文的模型细节大部分信息其实在架构图里（具体层的连接方式、分支的汇合点、哪些模块共享参数），正文文字往往只是粗略带过。处理方式：

1. 光栅化模型架构图所在页面，视觉读取图中每个模块、箭头方向、分支和汇合点
2. 回到正文，找模型结构对应的文字描述段落，逐句核对是否与图中信息一致——常见情况是图和文字两者各自包含一部分信息，必须合并才能拼出完整结构（比如图上画了某个模块，但维度信息、激活函数只在文字里写了；或者文字提到了某个细节但图上没画出来）
3. 如果图和文字出现矛盾（比如文字说有 3 层，图上画了 4 层），两者都要记录，标注为冲突，不要自己选一个写进文档而不说明
4. 最终模型结构必须用 **mermaid** 绘制成图，作为理解文档的一部分（不是用文字描述代替图，文字描述和 mermaid 图两者都要有）。mermaid 图要体现：
   - 每个模块的名称和维度变化（节点标签中标注 shape，如 `Embedding (B, 64)`）
   - 数据流方向（箭头）
   - 分支与汇合点（如有跳跃连接、多分支融合，必须在图中明确画出，不能简化成线性链）
   - 示例：
     ```mermaid
     graph TD
         A[输入 user_id, item_id] --> B[Embedding Layer<br/>B,64]
         B --> C[GNN Layer 1<br/>B,64]
         C --> D[GNN Layer 2<br/>B,64]
         B -.跳跃连接.-> E[特征融合<br/>B,128]
         D --> E
         E --> F[预测层<br/>B,1]
     ```

### 模块三：对比实验汇总

除了模型自身结构外，论文通常会和若干 baseline 方法做对比，这部分信息同样要结构化记录下来，作为后续「结果验证 skill」核对复现指标时的参照：

- **对比的 baseline 清单**：论文对比了哪些方法（逐个列出名称），每个 baseline 是否也在本次复现范围内（多数情况下只复现目标模型本身，baseline 数值直接引用论文报告值即可，不需要重新跑）
- **对比维度**：论文从哪些角度做对比（如不同数据集、不同指标、不同超参数设置下的消融实验）
- **对比结果汇总**：把论文报告的对比结果数值整理成表格，逐项标注来源（哪个 Table/Figure 编号）
- **用 mermaid 绘制对比结果概览图**：如果对比方法较多，建议用 mermaid 的图表或流程图形式可视化呈现各方法的相对关系或性能层级（例如用 `graph` 画出"方法 A → 性能优于 → 方法 B"的层级关系，或用文本表格配合简单的趋势性 mermaid 图），帮助审阅者快速抓住"论文的核心论点是谁比谁好、好在哪个维度"，具体形式按论文实际对比内容灵活选择，不强制固定图类型

**模块四：实现约束**
- 关键超参数（learning rate、batch size、epoch 数、optimizer 及其参数等，逐项标注来源等级）
- 训练设置（硬件环境、训练时长、是否有特殊的训练技巧如 warmup/early stopping）

### 第三步：自查清单

完成初稿后，在交付前自己过一遍：

- [ ] 是否每一条具体数值/细节都标注了来源等级？
- [ ] 模型结构的层级拆分是否对应论文中的图示（如果论文有架构图，逐层比对）？
- [ ] **是否对架构图、关键公式、表格做过页面光栅化的视觉确认，而不是只依赖文字提取？**（文字提取对这三类内容不可靠，这是检查清单里最容易被跳过但风险最高的一项）
- [ ] 损失函数公式是否完整还原（不要只写主损失，遗漏权重系数和辅助项）？
- [ ] 是否填写了 2.6「正则化技术清单」？是否搜索了全文中所有 λ/weight decay/dropout/early stopping/noise 等关键词，确认没有遗漏分散在各处的正则化手段？
- [ ] 是否填写了 2.7「初始化方式」？权重/偏置/Embedding 各自的初始化分布和参数是否都与论文一致，是否标注了具体的论文出处段落？
- [ ] 「正则化技术清单」中的每项是否都标注了 PyTorch API 注意事项？尤其是 `‖W‖²` 这类公式对应 `.norm(p=2).pow(2)` 而非 `.norm(p=2)`（少一个平方会导致正则化强度差一个数量级）这类高频陷阱是否已排查？
- [ ] **【新增】数据格式是否已核实**？是否 `head -3` 了原始文件并粘贴到 1.3「数据结构」中？每行是 `user item1 item2...` 还是 `user item` 成对格式？预处理代码的解析逻辑能否匹配？
- [ ] **【新增】代码来源层级是否已区分**？如果参考了代码，是 A 级（官方）、B 级（论文原文）还是 C 级（第三方）？C 级代码的任何行为是否已先回论文核实再采用？
- [ ] **【新增】攻击/投毒/对抗类论文的动态数据注入是否已标注**？论文是否包含注入假用户/假样本/对抗样本等步骤？如果有，理解文档是否在模块二中单独标注了哪些数据结构是静态的（如 N）、哪些是动态的（如 M 会随注入递增）、动态扩展的触发时机？
- [ ] 是否所有【AI推断补全】的内容都给出了推断依据，而不是只贴一个标签？
- [ ] 是否在文档开头汇总了所有"论文未提及"的关键缺口，方便用户在检查点①时重点关注？

### 第四步：交付与提示

交付文档时，明确告诉用户：

> 这份文档将作为后续代码实现的唯一依据。请重点核查标注为【AI推断补全】的部分（已在文末汇总），以及模型结构和损失函数部分是否与论文一致。确认无误后请明确告知"理解文档确认通过"，我会基于此继续生成代码骨架。

不要在用户确认前就继续往下走（生成代码骨架）。这是工作流里第一个、也是最重要的人工检查点。
